# 已知问题与技术债

本文件记录当前代码无法仅靠一次编译证明的问题，以及下一位维护者最容易误判的地方。

## 1. 厂商可能把 120 Hz 降为 60 Hz

当前代码已经同时请求显示模式、窗口刷新率和 Surface 帧率，并在玻璃球活跃时按每次 VSync 提交。但 OPPO、ColorOS、小米、HyperOS 等系统仍可能在用户停止触摸后，通过系统级动态刷新策略把应用悬浮层或合成链路降到 60 Hz。

应用层公开 API 只能表达偏好，不能保证 SurfaceFlinger 或厂商显示策略始终采用 120 Hz。排查时要区分：

- `Choreographer` 回调频率是否已降到 60 Hz。
- 应用是否仍每次回调调用 `submit()`。
- EGL 是否持续 `swapBuffers()`。
- 显示面板、窗口或合成层中哪一层被系统降频。

需要用目标真机、开发者帧率叠加、Perfetto/FrameTimeline 和 `dumpsys SurfaceFlinger` 验证。不要把“代码请求了 120 Hz”写成“所有设备保证 120 Hz”。

## 2. 系统背景模糊受平台能力限制

`Window#setBackgroundBlurRadius()` 只在 Android 12+ 可用，而且还受系统全局跨窗口模糊开关、GPU、节电模式和厂商实现影响。系统可能在运行期间关闭能力，代码会监听变化并安全隐藏模糊层。

玻璃球轮廓使用公开 API 能稳定表达的圆角矩形。Android 不提供任意 Path 形状的跨窗口模糊，因此极端拖动形变只能近似为实时圆角胶囊。下层渐变模糊由五个窗口条带近似，会增加合成层数量，也可能加剧部分厂商的降频策略。

## 3. 模糊与动画的性能取舍

玻璃球模糊窗口的几何更新间隔为约 8 ms，理论上可跟随 120 Hz；展开和收起转场中暂时禁用系统模糊，完全展开后再淡入。若恢复转场中实时模糊，必须先在中低端设备检查 WindowManager 更新、SurfaceFlinger 合成和 GL 提交是否互相争抢。

“下层模糊”和“玻璃球模糊”必须保持互斥；“下层变暗”是独立的纯颜色渐变，可以与任一种模糊叠加。

## 4. 目标 SDK 与输入区域

工程使用 `compileSdk 37`，但故意保留 `targetSdk 30`。精确形状触控依赖当前窗口输入区域实现，该路径在提高 target SDK 后可能受平台限制。结果是：

- 适合侧载调试，不满足现代应用商店的目标 SDK 要求。
- Android 12+ 当前还依赖用户开启无障碍服务来取得对应窗口上下文。
- 升级 target SDK 前必须重新验证状态栏/刘海区域触控、悬浮窗口类型和后台限制。

## 5. 全屏状态检测存在厂商差异

“全屏时隐藏”根据状态栏可见性和周期检查触发。沉浸式模式、游戏空间、视频播放器和厂商系统 UI 可能使用不同窗口策略。全屏隐藏/恢复阶段即使状态机已经是 `Collapsed`，也必须继续提交转场帧；不能只依据玻璃球状态决定是否渲染。

## 6. 横屏与异形屏必须真机验收

四向旋转已经统一到物理竖屏坐标，但刘海、挖孔、侧边导航栏、瀑布屏和 180° 旋转在不同 ROM 上仍可能返回不同 inset。任何 `OverlayLayout`、`RotationCoordinateSpace` 或窗口边界修改，都要至少检查 0°、90°、180°、270°，尤其是“手机向左倒”时的屏幕左侧位置。

## 7. 系统助手联动不是通用 API

无障碍服务只根据少量白名单包名和窗口元数据判断系统助手是否出现。ROM 更新可能更换包名、延迟挂载窗口，或完全不向第三方无障碍服务暴露对应窗口。此功能不能保证覆盖所有 OPPO、小米、vivo 或其他设备。

不要扩大到读取节点文字、截图、录音、按键或手势；若新增包名，应保留最小数据使用边界并在对应真机验证出现与退出两条路径。

## 8. 设置本地化仍有维护成本

大量设置文案在 `NativeSettingsUi.kt` 中动态生成，英文由 Kotlin 映射与资源文件共同维护。新增中文标签但遗漏英文映射时，英文系统会出现局部中文。长期可考虑把全部文案迁移到资源 ID，但迁移时不要牺牲完整行点击区域、滑杆触感和滚动位置。

## 9. 构建输出不在常规目录

根 Gradle 脚本把构建目录重定向到 `${java.io.tmpdir}/glass-orb-android-build`。`app/build/outputs/apk/debug/app-debug.apk` 可能是很早以前的残留，不能直接拿来发布。每次交付都必须查询实际 `buildDir`，核验 APK 的修改时间、包名、版本、签名和 SHA-256。

## 10. 当前 APK 只是 Debug 签名

`dist/灵动玻璃球-2.0.28.apk` 是侧载 Debug 包，不是商店 Release 包。正式发行需要单独的发布密钥、密钥保管方案、Release 构建类型、混淆/资源压缩评估和升级签名策略。

## 11. 自动化测试不能替代视觉验收

单元测试可覆盖状态、几何、策略和配置；仪器测试可覆盖部分像素与界面。它们仍不能证明厂商 120 Hz、真实跨窗口模糊、窗口层级、状态栏触控和系统助手联动。发布说明必须区分“构建/测试通过”和“目标真机人工验收通过”。

## 12. 非商业许可限制

玻璃 Shader 和动画行为参考固定开源仓库提交，但参考许可只允许个人学习、教育、研究及其他非商业用途。免费并不自动消除署名和许可义务，也不等于获得商业授权。不要删除声明、混淆来源或把当前代码直接改成商业版本；如需商业化，应先获得权利人的明确许可或以可证明的 clean-room 方式重新实现。
